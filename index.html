How the Drone Happened

What began as simple experiments with an F450 kit quickly grew into building a fully custom microdrone from scratch. Inspired by the Max Imagination YouTube channel, the team decided to stop using off-the-shelf boards and design every layer themselves.

The first custom motor driver PCB failed completely — wrong trace widths, power layout issues, and component selection errors. Instead of giving up, the design was reworked. The second revision brought it to life. Then came the soldering marathon: ESP32 Mini, MPU6050 over I²C, and four coreless motors wired to the custom driver.

Multiple open-source flight control programs were tested. PID tuning, sensor fusion, motor mixing — each iteration taught something new. Today, all four motors spin in coordinated response to IMU data. The drone prototype works.

Sunboard to Metal

This was CIA Labs' first ever robotics project — and it started the way most hardware projects do: with whatever materials were available. The initial prototype was built on a sunboard chassis, running an Arduino Uno as the brain, with basic DC motors and a rough wiring job that just needed to move.

It moved. But stability, controllability, and match-readiness were all missing. The chassis flexed under load. The wiring was unreliable. The motor drivers burnt out under sustained current draw. Arduino's processing limits became visible when trying to implement responsive motor control with any real logic.

So we did a full rebuild. Metal chassis fabricated from scratch. Wiring completely redone with proper gauge wire and secure connectors. New motor drivers rated for the actual current draw. And the brain? Swapped from Arduino to ESP32 — a decision that changed what the bot was capable of.

The flame-painted final version isn't just cosmetic. It represents every iteration that came before it.

// the upgrade

Why We Moved from Arduino to ESP32

This wasn't just swapping a chip — it was an architectural upgrade. Here's the technical breakdown of why Arduino hit its limits and what ESP32 unlocked for us.

// Before · Arduino Uno

The Limits We Hit

CPUATmega328P — 16 MHz, 8-bit. Single-core. Slow enough that motor control loop + sensor reads started competing for cycles.
RAM2 KB SRAM. Adding any logic buffer, PID state, or serial debug print would eat into available memory dangerously fast.
PWM6 PWM pins, timer-based. Limited resolution (8-bit by default). Conflicting timers caused PWM frequency interference between motor channels.
ConnectivityNo Wi-Fi, no Bluetooth built-in. Wireless control required external HC-05 Bluetooth module — extra wiring, latency, complexity.
Interrupts2 hardware interrupt pins (INT0, INT1). Insufficient for monitoring multiple encoder channels or collision inputs simultaneously.
Logic5V GPIO. Required level shifting to interface with 3.3V peripherals, adding components and potential failure points.

// After · ESP32

What It Unlocked

CPUXtensa LX6 — 240 MHz, 32-bit, dual-core. Motor control runs on Core 1. Sensor polling and logic run on Core 0. No more cycle contention.
RAM520 KB SRAM + 4 MB Flash. Enough to buffer telemetry, run PID state machines, and hold lookup tables without compromise.
PWMLEDC peripheral — 16 independent PWM channels, up to 16-bit resolution, configurable frequency per channel. No timer conflicts.
ConnectivityWi-Fi 802.11 b/g/n + Bluetooth 4.2 built-in. Enables OTA updates, web-based controller, and low-latency BLE gamepad input.
InterruptsAny GPIO can be interrupt-capable. Enabled encoder feedback on all 4 drive motors simultaneously without external hardware.
LogicNative 3.3V GPIO. Direct interface with modern sensors and modules. No level shifters, cleaner PCB, fewer failure points.
Core reason

PWM Timer Conflicts

On Arduino Uno, all PWM outputs share Timer0, Timer1, and Timer2. Running 4 motors caused frequency interference — motors would occasionally stutter or one channel would override another. ESP32's LEDC peripheral solved this with fully independent channels.

Core reason

Processing Bottleneck

At 16 MHz with a single core, the Arduino was spending ~40% of CPU time just reading encoder pulses and running the servo library. Adding any real game logic caused noticeable motor lag. ESP32's 240 MHz dual-core handled motor control on one core and all game logic on the other — independently.

Core reason

Wireless Control

The HC-05 Bluetooth module on Arduino added 20-30ms of communication latency and was notorious for dropping connections. ESP32's native BLE runs at under 10ms latency with a stable connection, directly from the chip — no extra module, no extra wiring, no extra failure point.

// what we fought

RoboSoccer Failures

🔥

Motor Drivers Burnt (Twice)

L298N drivers weren't rated for the sustained current draw of 4 motors under load. Burnt out during testing. Switched to properly rated drivers with adequate thermal headroom.

⚡

PWM Timer Conflicts on Arduino

All Arduino PWM channels share timers. Running 4 motors simultaneously caused frequency interference — random stuttering and one channel dominating others. Core reason for the ESP32 migration.

🏗️

Sunboard Chassis Failure

The initial sunboard chassis flexed under motor torque and cracked at mounting points during impact. Needed a rigid metal replacement.

📡

HC-05 Bluetooth Dropout

The external Bluetooth module on Arduino dropped connection frequently and added 20-30ms latency. Replaced by ESP32's native BLE — no module, lower latency, stable connection.

🔌

Loose Wiring Under Vibration

Hand-crimped connectors on the Gen 1 build came loose during matches from motor vibration. Gen 2 used soldered joints and strain relief throughout.

🧠

Arduino RAM Exhaustion

With 2 KB SRAM, adding serial debug logging alongside motor control filled memory. Variables would corrupt and behavior became unpredictable. ESP32's 520 KB eliminated this entirely.
